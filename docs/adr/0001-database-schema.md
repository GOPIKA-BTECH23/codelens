# ADR 0001: Database schema decisions (M1)

Status: accepted, 2026-10-15

## Context

M1 creates the Postgres schema (CLAUDE.md section 7), the job queue and the migration setup. Several choices are easy to get wrong and expensive to change later, so they are recorded here.

## Decisions

### 1. `EMBEDDING_DIM = 768`, defined once

`app/db/constants.py::EMBEDDING_DIM` is the only place the number is written. The `code_chunks.embedding` column type is `Vector(EMBEDDING_DIM)`. `Settings.embedding_dim` (env `EMBEDDING_DIM`) must equal it or the app refuses to start.

Why a constant and not a setting: the dimension is part of the table definition. Changing it requires (a) a migration that alters the column and rebuilds the HNSW index and (b) re-embedding every chunk. A runtime setting that can silently differ from the column would produce errors at insert time, deep in the indexing job. The startup check turns that into an immediate, obvious failure.

The initial migration writes `768` into its own file on purpose: a migration must describe the schema as it was at that point in history, even if the constant changes later.

### 2. Uninstall keeps review metadata; cascades are for hard deletes only

Foreign keys use `ON DELETE CASCADE` so that a deliberate hard delete (an admin removing a repository, a test cleaning up) cannot leave orphans. **An uninstall is not a delete.** On `installation.deleted` we:

1. set `installations.uninstalled_at`;
2. stop the installation's jobs;
3. delete **only** `code_chunks`, `chat_sessions` and `chat_messages` (the later purge job does this with explicit `DELETE` statements);
4. 30 days later, set `findings.message` and `findings.suggestion` to `NULL`.

(M6 adds `review_run_files.patch`, which holds source code and is purged on uninstall too and 30 days after a PR is closed or merged: ADR 0006.)

The installation, repository, pull request, review run and finding rows stay (CLAUDE.md section 7). Nobody may implement the purge as `DELETE FROM installations`; that would cascade away the metadata we promised to keep. A schema test (`test_uninstall_marker_keeps_installation_and_review_metadata`) pins the "setting `uninstalled_at` deletes nothing" half of this.

### 3. Chat ownership

`chat_sessions.repository_id` is `ON DELETE CASCADE` (chat data goes with its repository). `chat_sessions.user_id` is `ON DELETE SET NULL` and nullable: removing a user account must not silently erase a conversation about a repository other people may still use.

`chat_messages.cited_chunk_ids` is a `uuid[]`, not a join table. Chunks are replaced when files are re-indexed; an FK from messages to chunks would block re-indexing, and a citation to a replaced chunk is simply stale, which the UI can show.

### 4. `repository_access` is created in M2, not M1

CLAUDE.md section 7 and decision 13 both say the `repository_access` table arrives with the M2 migration, alongside the login code that syncs it from GitHub and the endpoints that enforce it. The M1 request said "every table in section 7"; the written decision log wins, and section 7 now states the exception explicitly. An empty, unenforced access table in M1 would look like an authorization guarantee that does not exist yet.

### 5. Enums are `VARCHAR` + `CHECK`, not native Postgres enums

Adding a value to a native enum needs `ALTER TYPE ... ADD VALUE` (awkward in a transaction) and values can never be removed. A `CHECK` constraint is a one-line migration. The allowed values live in Python `StrEnum` classes and the constraint is generated from them, so code and database cannot disagree.

### 6. UUID primary keys, GitHub ids as separate unique columns

Primary keys are UUIDs generated by Postgres (`gen_random_uuid()`), so they are not guessable or enumerable in URLs. GitHub's numeric ids (`github_id`, `github_installation_id`, `github_repo_id`) are `BIGINT` with `UNIQUE`, because they are what webhooks and API responses give us.

### 7. Search indexes

- Vector: HNSW on `code_chunks.embedding` with `vector_cosine_ops`, `m=16`, `ef_construction=64` (pgvector defaults, written down so they are a choice, not an accident). Queries must use the `<=>` operator or the index is not used.
- Full text: `tsv` is a stored generated column, `to_tsvector('simple', content)`, with a GIN index. The `simple` configuration skips stemming and stop words, which suits identifiers such as `get_user_id`.
- `pg_trgm` is **not** installed. Nothing in the planned milestones needs fuzzy matching; add it in the milestone that does.

### 8. Timestamps

`created_at` / `updated_at` use the database clock. `updated_at` is refreshed through SQLAlchemy's `onupdate`, which covers ORM changes and Core `update()` statements but **not** hand-written SQL. Application code therefore uses SQLAlchemy statements, and a test documents the limit. A database trigger would remove the caveat but adds hidden behaviour; revisit if raw SQL updates become common.

### 9. The job queue lives in Postgres

See `app/services/jobs.py`. Claiming is a short committed transaction (`FOR UPDATE SKIP LOCKED`, set `running`, commit); handlers run outside any transaction. `enqueue` takes the caller's session so that webhook intake can record the delivery, create the review run and enqueue the job atomically. Stale `running` jobs are returned to the queue after a visibility timeout, and `attempts` is counted at claim time so a job that keeps crashing its worker still ends up `dead`.

### 10. Extensions and downgrades

The initial migration runs `CREATE EXTENSION IF NOT EXISTS vector`. Its downgrade drops the tables but leaves the extension, because extensions are database-wide and something else may use them. Supabase installs extensions in the `extensions` schema; check that `vector` resolves there when we deploy (M7).

## Consequences

- Changing the embedding model dimension is a deliberate, multi-step operation.
- Retention code in later milestones must use targeted deletes, never installation deletes.
- Every schema change from here on needs a reviewed migration; a test fails if models and migrations drift.
